### OS: malloc(32 KiB) trace — first pass
- Got: libc serves from arena or calls brk; MOV -> walk -> #PF, CR2 = faulting address; kernel fills PTE; instruction re-runs.
- WRONG: "arena (the stack assigned to the process)" — arena = malloc's heap region (main arena grows via brk), not the stack.
- Missing: 128 KiB mmap threshold (why brk here, not mmap); brk only extends the heap VMA, no frames; overcommit.
- Missing: what the fault handler checks = the VMA (inside a VMA with write permission -> allocate a ZEROED frame; no VMA -> SIGSEGV). "sees it is not assigned" conflates VMA and PTE.
- Missing: chunk header written by malloc just below the pointer -> first page may already be present, the int write may not fault. TLB fill not mentioned.
- Missing: exit (VMAs torn down, frames + page tables freed).
- Probe 1 (arena): recovered — "heap of the process, called the arena". OK. Precise: glibc's main arena = brk heap; other threads' arenas = mmap'd heaps.
- Probe 2 (fault check): "a struct for all the RAM addresses, what has been written where and with which permission" — vague and partly wrong: it's per-process mm_struct -> VMAs (vm_area_struct: range, perms, backing), virtual not physical, nothing about "what has been written". Never named VMA.
- Probe 3: KEY MISCONCEPTION — "one global table for the whole RAM, describes both physical and VA; brk assigns physical addresses to the process". Wrong on all three: VMAs are per-process + virtual; struct page array is the global physical one; brk only moves mm->brk / extends the heap VMA, no frames. Corrected in-round. This was in the OS 2 review sheet (Mon 26) -> revisit os1_os2_review.md tonight.
- Probe 4 (does the int write fault?): "malloc almost never faults, so probably not" — right verdict, wrong reason (mixed up "rarely returns NULL" with "rarely faults"). Real reason: malloc writes the chunk header just below the pointer -> that write takes the fault, the page is present when your int lands (same page unless at a page boundary).
- Probe 5 (exit): "page tables, mm_structs gone; frames interpreted as free since the process doesn't exist" — WRONG model (no lazy reclaim by owner lookup). exit_mmap walks VMAs/PTEs, drops each page's refcount/mapcount, a frame returns to buddy free lists when refcount hits 0 (shared libc text / page cache stays), page tables freed, TLB flushed, mm freed when mm_users -> 0.
### OS: "inside a guest" follow-up
- Got: two-stage translation, every guest walk also translated through host tables (2D walk). Good.
- Vague: "two set of pages" -> should be: guest page tables (GVA->GPA, owned by guest) + EPT (GPA->HPA, owned by KVM).
- Missing so far: guest #PF is handled by the GUEST kernel, no VM exit (with EPT); unbacked GPA -> EPT violation -> VM exit -> KVM.
- Q1 right: guest kernel handles its own #PF via its own mm/VMAs, no VM exit. Good.
- Term error: "VMM owns the shadow pages" — shadow page tables are the pre-EPT software scheme (KVM builds GVA->HPA, traps guest PT writes). With EPT: guest owns guest PTs (GVA->GPA); KVM (host kernel) owns EPT (GPA->HPA); userspace VMM owns the HVA mapping of guest RAM, registered as memslots (GPA->HVA).
- Q2 (unbacked GPA -> EPT violation) not answered yet.
- Q2: "host backs the address through its kernel for the VMM process, then guest assigns GPA to GVA" — right that the host fault is in the VMM's address space; order reversed (guest PTE already done); missing: EPT violation VM exit, faulting GPA from the VMCS, memslot GPA->HVA lookup, host fault on HVA (hva_to_pfn / GUP), EPT entry installed, VM entry, instruction re-executed, guest sees only latency.

### Design: live migration — first proposal
- Asked a good clarifying Q (is it live / any quiet time?), but only one; didn't ask about size, storage, network, downtime budget before designing (I volunteered them).
- Proposal: network switch in front buffers client traffic; snapshot VM on A, copy to B, keep running on A, short buffer, flip switch to B; one VM at a time.
- Problems: snapshot goes stale while A keeps running (no dirty tracking / convergence); no numbers (512 GiB @ 25 Gbps ~ 165 s); buffering traffic for the copy breaks the pause budget; nothing on vCPU/device state, TSC, storage re-attach, what triggers the cutover, failure/rollback.
- Good instinct: a mapping layer in the network that decides which host owns the VM (≈ VPC mapping update / GARP).
- Math: said 22.5 s; correct ≈ 512 GiB × 8 bit / 25 Gbit/s ≈ 4400 Gbit / 25 ≈ 176 s (~3 min). Forgot bytes -> bits. Always say units aloud.
- Good: reinvented pre-copy + final patch ("buffer the changes, apply on B, hold traffic during the patch") = stop-and-copy. Unproven: "cannot be much compared to the whole system" (write-heavy guests). Mechanism to know WHAT changed not named yet.
- Self-corrected units (good). 2 GB/s × 180 s = 360 GB -> 115 s more: right arithmetic, but treats dirty data as a byte stream; it's a SET of pages (rewrites of the same page count once; bounded by the writable working set). Ratio 16/25 per round converges geometrically if dirty rate < link rate.
- Dirty mechanism: "hypervisor sees pages through its own page tables" — direction right (EPT), mechanism not named: write-protect EPT / EPT dirty bits + PML -> dirty bitmap (KVM_GET_DIRTY_LOG / dirty ring), cleared per round.
- Fallback "wait for a quiet window" contradicts the premise (no window). Missing convergence tools: iterate rounds, throttle vCPUs (auto-converge), post-copy, compression/zero-page skipping, cap + abort.
- 'diff current state vs snapshot' — would mean reading/hashing 512 GiB each round; stuck on mechanism -> gave hint (dirty bit / write-protect).
- Got write-protect -> fault -> log (after hint). Imprecise: 'transfer the logs' -> transfer the CURRENT CONTENTS of the pages in the dirty bitmap, not a log of the writes.
- Stop criterion: "at some point there's no other way" — no rule. Expected: stop when remaining dirty bytes / bandwidth < downtime budget (or rounds stop shrinking / max rounds); levers: throttle vCPUs (auto-converge), post-copy, zero-page + compression, abort and retry or pick another target.
- State to move: "RAM, the page tables, all registers". Guest page tables are guest RAM (already copied); EPT is NOT moved, B rebuilds it lazily. "Registers" vague: GPRs, CRs, MSRs, XSAVE/FPU (Stanislav's area!), LAPIC + pending interrupts, TSC offset. Missing: device state (virtio rings, in-flight I/O), storage re-attach, network cutover, failure/rollback.
- Stop rule: roughly right after unpacking (pause when remaining dirty / bandwidth ≤ budget, with margin) but stated backwards ("when the time exceeds the deadline"). "4× + bootup of B": B does NOT boot — destination VMM is started first, receives state, RESUMES the guest.
- EPT: WRONG — "should be sent". EPT maps GPA->HPA of host A; A's HPAs mean nothing on B. B builds its own EPT lazily (EPT violations after resume; post-migration warm-up cost).
- vCPU: "regs and sregs" (KVM_GET_REGS/SREGS) good start; missing MSRs, XSAVE/FPU, LAPIC, pending events, TSC.
- Never covered: devices (virtio queue state, drain in-flight I/O), storage re-attach, network cutover, failure/rollback (A keeps the source until B confirms; abort = resume on A).
- Failure: right — A stays authoritative until cutover, B crash = abort, guest keeps running on A, retry to another target. Missing: the commit point (B acks full state -> only then A releases), and crash AFTER pause = resume on A.
- Network cutover: "packets go to B if the VM is marked migrated" — right idea, no mechanism: update the VPC mapping (IP/MAC -> host B) or B sends gratuitous ARP/RARP; packets lost during the pause are retransmitted by TCP, which is why connections survive.
